# Limitations

Read this before trusting a score. The short version: it is a cheap first filter that looks only at the name of a domain. It finds about half the phishing hosts of its test data at a 1% false-alarm rate, and it says nothing about a page.

- **It reads the registrable domain, not the page.** Only the registrable domain (`example.co.uk`), the user info and the port are scored. The path, the query, the scheme, `www.` and other subdomains are ignored. A phishing page on a legitimate host (a document on a file-sharing site, a form on a free hosting service) is scored as that host. A URL shortener hides its target. Nothing is fetched, so redirects, page content, certificate, domain age and reputation lists are all outside what it knows.
- **Subdomain tricks are warnings, not score.** `paypal.com.example.net`, `@` before the host, an IP address, an unusual port, a shortener, punycode and four or more subdomain levels are found by plain rules and printed next to the score. When the score is under the threshold but a rule fired, the verdict is `suspicious`. When nothing fired, `legitimate` means "no sign found", not "safe".
- **Why not the path?** In the public dataset used here (PhiUSIIL), none of the legitimate test URLs has a path: they are bare domains, against 16.81% of the phishing ones. A model that sees the path learns "has a path = phishing" and scores 99.9% on that dataset, and would flag every ordinary page of a real site. That version was built and measured first (`docs/evaluation.md`, section 3).
- **Why not `http` or `https`?** Every legitimate URL in the dataset is `https` (and starts with `www.`), against 44.65% of the phishing ones. The rule "not https means phishing" catches 55% of them with no false positive at all, and adding the scheme to the model lifts its recall from 52% to 86%. But today most phishing is also served over `https`, so a model relying on it would trust phishing it should not. The scheme is ignored, including in lengths and ratios (an earlier attempt that only dropped the scheme column still leaked it through the lengths, and looked 23 points better in recall than it was).
- **Why not the subdomains?** Only 3.14% of the legitimate test URLs have one (besides `www`), against 30.24% of the phishing ones. Real sites use `mail.`, `accounts.`, `cdn.`. Scoring them would flag those.
- **The legitimate class is popular sites.** The "legitimate" URLs in the dataset are well-known domains. The model learns to tell a name that looks like one of those (short, pronounceable) from one that does not. A small, ordinary, legitimate site with an odd name is exactly what it is likely to flag, and the evaluation says nothing about how often. The 1% false-positive rate is the rate on popular sites.
- **Precision depends on how common phishing is.** The test part is 39% phishing. On real traffic phishing is rare. With the measured rates (recall 0.522, false-positive rate 0.0107), if 1 URL in 100 is phishing, only about 33 of every 100 flagged URLs are phishing: 0.522 x 0.01 / (0.522 x 0.01 + 0.0107 x 0.99). The 96.9% precision in the report is for the 39% mix.
- **The dataset has no dates.** It cannot be split by time, so the figures do not say how fast the model goes stale. Phishing hosts change names quickly; retrain on fresh data.
- **Text only.** An attacker who picks a plausible, dictionary-like domain name defeats lexical features, and look-alike names of real brands (`paypa1.com`) are caught only if their letters look unusual. Look-alikes in other scripts are flagged as punycode.
- **A score is a probability under this model and this data**, not a verdict. The threshold was chosen so that 1% of the legitimate validation URLs are flagged; on the test part it flagged 1.07% (95% interval 0.93-1.22%).
- **Hashing.** Character 3-grams are folded into 32,768 buckets, so two different 3-grams can share a weight. The explanations show the token that was present, not proof that it caused the score.
- **The local API has no authentication.** Keep it on `127.0.0.1`.
